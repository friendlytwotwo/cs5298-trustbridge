# TrustBridge 四节点委员会演示 — 通过判据（判级 L2 / L1 / L0）

## 0. 用途与证据纪律

本文件回答一个问题：**怎样算"四节点委员会认证"真的跑通了？**

两条硬规则：

1. **只认两类证据**：① console 原文行（`shaker console` 输出，取证源 node1）；
   ② 链上读回（`deal_info` / `balance_of` / `e2_net_config`）。
   交易状态码（status=0x1）**不是**效果证据（见 §4）。
2. **判级口径的出处**：`workflow-out/_plan-prev-r3-backup.md` §3.4 第 5 点
   「参与度分级结论表」（:108 节起；第 5 点在 **:116**，三层定义 **:117-:119**，
   fallback 触发条件 **:121**）。
   `workflow-out/plan.md` 按阶段覆盖写，全案冻结条款与 §3.4 以该备份件为准。

本轮（R3-T3，2026-10-30）判级 = **L2**：`inputs=4` + `signers=4`
（`workflow-out/w1b2-r3-e2-committee.md:47-58`）。本文件同时给出 L1/L0 的验收形态，
供未来环境降级时使用。

## 1. 判级口径（三层定义）

| 级别 | 定义（§3.4 原文要义） | 原文位置 |
|---|---|---|
| **L2（目标形态）** | **4 提案（inputs=4）+ 4 签（signers=4）**。编排前提：`e2_arm` 只发一次（network 域单发全节点生效）+ node1 单次触发 + `avg_num=4`。机制依据：propose 经 UPC 广播，单次触发即全部委员会节点各出一提案。**不可多次触发**——N 次触发 = N 个独立回合，首回合裁决已把 deal 从 Disputed 推到终态，后续 certified call 必败。 | `_plan-prev-r3-backup.md:117` |
| **L1（可接受的四节点签署）** | **1 提案 + 4 签（signers=4，avg_num=1）**。签名集来自全部 4 节点即"四节点签署"成立；独立检视叙事由 propose 的证据派生承载（提案节点跑检视，其余节点签各自 replay 的同一聚合）。 | `_plan-prev-r3-backup.md:118` |
| **L0（平台硬限制）** | `threshold>1` 时 certify 无法聚齐（`run_round` 恒 false / `signers` 恒 1）——路线②只能单签送达。**降级处置 = 三段式诚实报告**：平台限制登记 + 单签 certified call 打通 + 路线①现状；演示与手册按实际级别描述。 | `_plan-prev-r3-backup.md:119` |

**降级触发条件**（`_plan-prev-r3-backup.md:121`）：T3 首跑提案数 <4（UPC 广播聚合不如预期）
→ 改 `avg_num=1`（L1 口径）+ **重新 cp/deploy**（编码期常量改值需重部署）→ 按 L1 取证并显式登记；
若 signers 也聚不齐，按 L0 三段式处置。

**诚实红线（任何级别都不例外）**：绝不把"单签"写成"四节点认证"、绝不把 L1 写成 L2。
判级结论必须能由 console 原文行直接读出，不能靠推断。

## 4. 通用纪律（判级时最常踩的三个坑）

1. **status ≠ effect**。交易 status 为 `0x1` 不等于状态转移成功。
   活例（R2）：`apply_committee_verdict` 交易 status 0x1，但 deal-4 仍停在 `Disputed`
   ——平台吞掉了内层 Err（`workflow-out/_r2-adversarial-raw.txt:6`）。
   一切以 `deal_info` / `balance_of` 读回为准。
2. **两段 `agreed` ≠ 两次裁决**。console 的 aggregate 行在 :24 与 :29 出现两次
   （同一 4 输入集的重复回放），但 `certified call submitted`（:30）、
   `committee_verdict_certified`（:31）、`apply_verdict`（:36）各仅一次 → 无重复结算
   （`workflow-out/w1b2-r3-e2-committee.md:87-89`）。
3. **pending 与硬失配要分开**。arm 读回的中间空值 / 终态仍为 `Disputed` = pending，继续等；
   出现第三种值 / 其他终态 = 硬失配，立即 abort。两类语义在
   `scripts/demo.py:147-176`（`wait_for`）与 `:659-669`、`:686-695` 中有明确区分——
   判级时不要因为"等了一会儿没变"就下结论，也不要在硬失配后重试。

### 5.1 L1（1 提案 + 4 签）

### 5.2 L0（平台硬限制）

触发：`threshold>1` 时 certify 聚不齐（`run_round` 恒 false / `signers` 恒 1），
L1 也不可达。交付形式 = **三段式诚实报告**：

1. 平台限制登记：console/transcript 证据显示 certify 无法聚齐（附原文行）；
2. 单签 certified call 打通：证明"送达与结算"链路可用（signers 长度=1 的 console 行 + 读回终态）；
3. 路线①现状：R2 地址制委员会（Malicious / NotFulfilled / Fulfilled 三场景）既有结论。

**绝不**把 L0 的演示写成"委员会认证"；手册与判据必须按实际级别描述（`_plan-prev-r3-backup.md:119`）。
