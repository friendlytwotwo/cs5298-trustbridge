# CS5298 Final Project 方向总结：A2A 信任桥

> 整理日期：2026-10-08
> 选题：在 Lyquor 网络上实现面向 AI Agent 之间交易的信任保障层
> 状态：方向已定，待第一周平台验证（spike）

---

## 1. 一句话定义

在 Lyquor 上实现一个**面向 AI Agent 之间交易的信任保障层**：Agent 之间照常走现成的通信协议（Google A2A / MCP），但每一次交易的**授权、资金托管、履约存证、结算与超时赔付**由链上的 Lyquid 强制执行——让两个互不信任的自主 Agent 能完成交易。

**核心卖点：中介作为协议，而不是平台。** Web2 的中介（淘宝、App Store）本身是需要被信任的公司；把中介做成 Lyquor 节点/委员会后，信任对象从"一家公司"变成"可验证的协议"。

## 3. 选题逻辑

### 3.1 评判框架（三条标准）

1. **需求成立**是前提，但不够；
2. **Why Web3**：应用的哪些环节必须上链？（防伪、明确产权、去信任中介）
3. **Why Lyquor**：为什么必须部署在 Lyquor 而不是以太坊？

### 3.2 Why Lyquor 的论点

以太坊等主流链的智能合约只能做确定性小计算，复杂运算（AI 推理、大 SaaS）在链下完成后仅回传结果，**链上链下割裂**。Lyquor 把链下复杂服务与共享状态、资产、多节点协作**放进同一个可编程单元（Lyquid）**。因此选题应聚焦：**大运算的链下部署 + 防伪/产权**。

### 3.3 四个建议方向评估（为什么自选方向）

| 方向 | 评估 |
|---|---|
| 1. AI 预测市场 | 最简单但预计最多人选；创新空间小、区分度低，而评分创新占比很重；Lyquor 优势不明显 |
| 2. 跨链流动性聚合 | 工程量最大，跨链联调 + 测试网环境不可控 |
| 3. 可验证索引器 | 本质是可信 AI 问题（与 TEE 思路同源）；机制由平台原生提供，创新易被评薄 |
| 4. 抗 MEV 自适应 AMM | 理论最深，需对抗仿真支撑，六周内风险高 |

难度排序 **3 > 4 > 2 > 1**。综合判断：避开方向 1 的赛道拥挤，选四方向之外的 A2A 方向——与 Lyquor 能力高度契合，可争 E1 加分。

## 4. 核心设计

### 4.1 三层定位（关键：信任层，不是通信层）

| 层 | 管什么 | 谁负责 | 是否本项目核心 |
|---|---|---|---|
| 通信层 | Agent 发现与消息传递 | 复用 Google A2A / MCP（链下） | ❌ 直接复用 |
| **信任层** | 承诺凭什么算数：托管、授权、结算、超时赔付 | **本项目的 Lyquid + 合约** | ✅ **核心** |
| 计算层 | 资格审查、任务估时等复杂判断 | LLM 跑在 Lyquid 实例状态/私有计算 | ✅ Lyquor 优势所在 |

类比：淘宝的核心不是聊天工具，而是支付宝担保交易。本项目给 A2A 世界做"担保交易"这一层。

### 4.2 示范场景（版权授权市场）

```
Alice(视频创作者)                    Bob(歌手)
     │ Agent A                        Agent C
     │  ① 向中介发起报价                │
     │ Agent B(中介, Lyquor节点)        │
     │  ② 审查 A 资格(LLM)             │
     │  ③ 向 C 发起请求 ────────────────→ ④ 接受报价
     │  ⑤ 资金托管 → 签约(链上) ←────────────┘
     │  ⑥ 授权生效 / 到期 / 超时退款(合约强制)
```

### 4.3 上链对象与保障机制

- **上链**：授权、资金承诺、最终许可、结算状态、A↔B 关键消息的**哈希存证**（可验证执行）
- **合约强制校验**：授权是否过期、金额是否超限、是否允许退款
- **超时机制**：任务带时限；由平台内置 LLM/SaaS 估计可能用时，设计超时处理方案
- **中介节点化**：中介 B 直接作为 Lyquor 节点，委员会背书其裁决

### 4.4 问题定义（报告 Problem Analysis 的正确写法）

- ❌ 错误写法："Agent 之间需要一种新的通信机制"（通信链下好好的，Why Web3 答不上来）
- ✅ 正确写法："**高度自主的 Agent 之间直接交易时，没有可信中央平台做担保——谁保证付了钱拿到授权？谁保证服务超时会赔付？**"

## 5. 竞品与差异化

2025–2026 年 agent 商务协议已收敛为三层栈：

| 协议 | 阵营 | 管哪层 |
|---|---|---|
| ERC-8004 | Ethereum 标准 | Agent 身份/信誉 |
| x402 | Coinbase（AWS 已采用） | 稳定币机对机微支付轨道 |
| AP2 | Google | 授权委托（配合传统支付轨道） |
| A2A / MCP | Google 等 | 通信与工具调用（链下，本项目复用） |

**本项目的空档：履约过程可信**——通信哈希存证、任务估时与超时强制执行、托管结算。这些恰好是纯以太坊方案（合约只管状态与资产）做不了、需要 Lyquor 复杂链下运算绑定才行的能力。

报告需放三层对照表，明确"每层谁在做、我们补哪层"——这是 A2 创新分（10 分）与 E1 加分（10 分）的论证基础。

## 6. Lyquor 平台支撑

### 6.1 平台要点

- Lyquid = Rust 编写 → WASM 模块 → OCI 打包 → `shaker` 部署；运行于 lyquor-vm（wasmtime fork）
- **双状态模型**：网络状态（共识、确定性、带版本）+ 实例状态（节点私有、允许非确定性）
- **三类函数**：网络函数（全节点重放）/ 实例函数（节点本地，类 off-chain worker）/ **UPC 函数**（聚合式远程调用 = "多节点共同背书"原语）
- 官方资料：docs.lyquor.dev（Litepaper、Lyquid Flow 白皮书、基础设施白皮书）；GitHub org `lyquor-labs`

### 6.2 能力映射（文档已预验证，spike 确认 API）

| 待验证项 | 文档证据 | 状态 |
|---|---|---|
| 多节点共同背书 | UPC 函数 | ✅ 机制存在，验证 API 用法 |
| Lyquid 内调 LLM | `lyquid-llm` crate + `http` 模块 | ✅ 官方一等支持 |
| 状态建模 | `state!` 双状态模型 | ✅ 授权/托管=网络状态；审查/估时=实例状态 |
| 定时/超时 | `trigger!` 宏 | ⚠️ spike 确认定时语义 |
| 资产原语 | 未知 | ⚠️ 若无则 Lyquid 内部记账（demo 可接受） |

### 6.3 开发环境

- 依赖：Docker + Docker Compose + Git（`gh` CLI 认证拉 GitHub Packages）
- `docker-compose up -d` 起：Lyquor 节点（带 Anvil）+ 工具容器 + devnet 初始化容器
- `cargo generate` 建项目 → `shaker deploy` 部署；容器内经 `node:10087` 连节点
- SDK：`lyquid`（核心）、`lyquid-flow`（工作流原语）、`lyquid-llm`（LLM 集成）、`lyquid-test`、`lyquid-examples`

## 8. 难度评估与风险

**难度 ★★★（中等）**：理论难度为所有选项最低（无机制设计、无量化建模），难度形态是**宽集成**——3 个 Agent 端 + Lyquid 核心 + LLM + 多节点编排，每块不深但联调面宽。

| 风险 | 等级 | 缓解 |
|---|---|---|
| E1 "幼稚方向"倒扣 | 高 | 单一场景做深 + 三层竞品对照表，每个上链环节答 Why Web3、每个链下运算答 Why Lyquor |
| LDK 平台年轻、无前人经验 | 中 | 第一周 spike 提前引爆；问题只能靠官方文档/源码/课程材料 |
| 范围失控（"每个环节加保障"是无底洞） | 中 | 只做版权授权一个闭环；正常流程 + 1–2 个对抗流程 |
| LLM 非确定性 vs 可复现性（B1） | 中 | LLM 响应缓存/录制回放；测试走 mock，demo 走真实调用 |
| Demo 现场事故 | 低 | demo 提前预录（任务要求本就预录 3 分钟） |
