### 2.1 同步源码到容器

```bash
MSYS_NO_PATHCONV=1 docker exec multi-tools rm -rf /tmp/tb-lyquid
MSYS_NO_PATHCONV=1 docker cp lyquid/. multi-tools:/tmp/tb-lyquid
```

两条命令均应 `exit 0`（实录 `_r3-t3-deploy-raw.txt:57-58`）。但 **`exit 0` 不能证明 rm
删对了目标**：实录 :57 的原始命令缺 `MSYS_NO_PATHCONV=1` 前缀，那是照引实录原样；本手册已按
§1.1 规则补正。

**前缀必须带**：Git Bash 会把 `/tmp/tb-lyquid` 参数改写为宿主 Temp 路径，`rm` 在容器内
等于空删（`-f` 掩盖、仍 exit 0）、旧目录存活，`docker cp` 随后**合并进陈旧树**；§2.2 的
九文件勾稽只覆盖指定路径、对容器内多余残留是盲的，会破坏「容器里编的必须就是仓库里的字节」
这一保证。

### 2.2 md5 勾稽（宿主 ↔ 容器，9/9 MATCH）

```bash
# 宿主
md5sum lyquid/src/*.rs lyquid/Cargo.toml lyquid/Cargo.lock
# 容器（sh -c 承载 glob）
MSYS_NO_PATHCONV=1 docker exec multi-tools sh -c \
  "md5sum /tmp/tb-lyquid/src/*.rs /tmp/tb-lyquid/Cargo.toml /tmp/tb-lyquid/Cargo.lock"
```

预期 9 个文件逐个 MATCH（7 个 `.rs` + `Cargo.toml` + `Cargo.lock`）。实录 9/9 MATCH，
含新模块 `committee_certified.rs 83e358ee…`（`_r3-t3-deploy-raw.txt:91-123`）。
**不 MATCH 就不要 deploy**：容器里编的必须就是仓库里的字节。

### 2.3 编译门（强制重编）

```bash
MSYS_NO_PATHCONV=1 docker exec multi-tools sh -c "touch /tmp/tb-lyquid/src/*.rs"
MSYS_NO_PATHCONV=1 docker exec -w /tmp/tb-lyquid multi-tools \
  cargo check --target wasm32-unknown-unknown
```

预期 `Finished dev profile … in 5.72s`（实录值）、`exit 0`。输出中**唯一一行 `error:`

crate 的编译错误，构建会继续并成功（R2 部署日志同款）。

D-T3-1 修复（R3-T6）把「faucet 之后立刻快照」改成「先确认 faucet 落账、再快照」。

```python
tapped = wait_for(node, faucet_landed, timeout_s=15.0, interval_s=1.0,
```

### 3.5 单次纪律

同一条 deal 的 `e2_run_verdict_round` **只触发一次**（`scripts/demo.py:674-680` 的注释与
检查）。首次裁决已把 deal 从 `Disputed` 推到终态，再次触发是另一个回合、必败。
任何 RuntimeError 都是证据，不是重跑理由——先看 console（§4）再决定。

| :5 | `e2_configure: staged committee of 4 nodes threshold=4`——认证域已暂存 4 节点 |
| :6 | `e2_net_config: {"armed_deal":"", "current":{...4...}, "staging":{...4...}}` |
| :7 | `assess_brief: mode=heuristic report={...}`——链上评估回放 |
| :8-:13 | `deal_info` 读回序列（含重复读：Qualified ×2、Funded ×2）→ `Disputed`；:10 为 `fund:deal_view` 行 |
| :15 | `e2_arm: armed_deal=deal-1 (network domain; single send visible to all nodes)`——**arm 一次** |
| :14/:16/:17 | `e2_net_config` 读路径从 `""` → `""` → `"deal-1"`（滞后一块的中间值，见 §4.5） |
| :18 | `e2_run_verdict_round: … starting propose_and_certify (avg_num=4)`——**单次触发** |
| :19 | `e2_propose: … deal=deal-1 verdict=1 (shape_ok=false, entries=3, avg_num=4, …)` |
| :20-:23 | `e2_aggregate: input from Node-… -> deal=deal-1 verdict=1` ×4（四个**不同** NodeID） |
| :24 | `e2_aggregate: agreed deal=deal-1 verdict=1 from 4 input(s) (avg_num=4)`——**inputs=4** |
| :30 | `e2_run_verdict_round: certified call submitted to the sequencing backend`——certified call 只提交一次 |
| :31 | `committee_verdict_certified: cert.signers RAW = [0, 1, 2, 3] (len=4) …`——**signers=4** |
| :32-:35 | `committee_verdict_certified: signer N -> Node-…` ×4（四条映射，互不相同） |
| :36 | `apply_verdict: deal=deal-1 verdict=1 misconduct=[]`——裁决落账一次、misconduct 未增 |
| :37 | `committee_verdict_certified: applied deal=deal-1 verdict=1 signers=[…]` |
| :38 | `deal_info: {…, "state":"Refunded", …}`——终态 |

### 4.4 怎么向用户讲这一屏（认证从哪来）

1. 先指 :18-:23：一次触发后，**四个不同节点各出一份提案**（`input from Node-…` 四行）；
2. 指 :24：`agreed … from 4 input(s)`——四份输入一致才聚合成一个裁决；
3. 指 :30-:31：聚合结果只以**一个** certified call 提交，证书里 `signers RAW=[0,1,2,3]`（4 个签名者）；
4. 指 :32-:35：四个签名者索引逐个映射为四个**互不相同**的 NodeID（身份闭环，不是同一节点重复签）；
5. 指 :36-:38：裁决只应用一次，`misconduct=[]`（NotFulfilled 不加分），终态 `Refunded`。

一句话：**裁决不是某个脚本喂进去的**，而是四个节点各自检视链上证据后、由平台认证聚合、
以 4 签送达的单次 certified call（详见 `workflow-out/w1b2-r3-e2-committee.md` §T3）。

### 4.5 两个常见读屏误判

- **两段 `agreed` ≠ 两次裁决**：:24 与 :29 是同一 4 输入集的重复回放（console 重放窗口），
  而 `certified call submitted`（:30）、`committee_verdict_certified`（:31）、
  `apply_verdict`（:36）各只出现一次 → 无重复结算
  （`workflow-out/w1b2-r3-e2-committee.md:87-89`）。
- **`armed_deal` 的中间空值 = 读路径滞后**：:14/:16 仍为空、:17 才是 `deal-1`；
  读回纪律是轮询到目标值，**绝不因中间空值重复 arm**（`scripts/demo.py:652-669`）。
